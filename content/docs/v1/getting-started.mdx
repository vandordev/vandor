Generate a new project, inspect the folder layout, and begin implementing your first bounded context.

## Install vx

Install the CLI first, then verify that the binary is available in your shell.

```bash
go install github.com/vandor/vx/cmd/vx@latest
vx version
```

For dummy content purposes, assume the command now points to the `v1` workflow family.

## Bootstrap a new service

`v1` starts to emphasize a more repeatable team workflow. Instead of just creating a shell, the init step prepares a structure that can be shared across multiple services.

```bash
vx init orders-service --module github.com/acme/orders-service
cd orders-service
```

You now have a service root that is ready for bounded contexts, adapters, and application orchestration.

## Create a domain slice

Pick one business area and generate it as an isolated slice of the service.

```bash
vx generate context orders
vx generate usecase orders create-order
```

This gives you a basic place for commands, orchestration, and domain-facing interfaces without mixing them into HTTP handlers directly.

## Generate infrastructure pieces

Once the application flow exists, add only the adapters you need.

```bash
vx generate adapter http
vx generate repository postgres
```

The goal is to keep implementation details behind interfaces so the core business flow stays stable while adapters change.

## Review the project shape

The generated project should roughly resemble this:

```text
cmd/
internal/
  domain/
    orders/
  app/
    orders/
  adapter/
    http/
    repository/
pkg/
```

Even as a dummy example, this is the main value proposition of `vx`: a service starts with boundaries that are already legible.
